Order Anomaly Detection

WHY IT STARTED

Order flow is a business signal that infrastructure health alone cannot explain. A platform can remain reachable while an order journey behaves unexpectedly, so monitoring needs a way to identify unusual business activity as well as failing components.

The problem addressed by this implementation was the repeated comparison of the latest order figures with historical behavior across multiple reporting entities. Reviewing each observation individually makes detection dependent on when an engineer looks and how consistently that engineer interprets normal variation.

I implemented an analysis pipeline that applies the same preparation, scoring, and presentation steps to each input. The purpose was to move from repeated manual comparison toward an automatically prepared set of investigation candidates. The resume reports reduced mean time to detect through automated alerts and reporting; it does not supply a timed before-and-after study.

WHAT CHANGED

The operational task requires collecting counts, comparing them with expected behavior, deciding which deviations matter, and preparing an explanation for the team. Without a consolidated pipeline, those are separate review and communication steps.

A single processing path loads an export, derives comparable features, runs detection, assigns severity, generates CLI and HTML output, sends the configured alert, and archives the processed input.

IMPLEMENTATION DECISIONS

Combine different detection methods
The implementation runs Isolation Forest, Local Outlier Factor, and One-Class SVM against standardized features. In the reviewed V4 path, at least two model votes are required for an ensemble anomaly. This makes the decision a defined consensus rule rather than a single unexplained flag.

Preserve an explanation alongside a flag
Mean, standard deviation, latest count, Z-score, latest-to-mean ratio, and coefficient of variation provide context that operators can inspect. Severity and the reporting layer make the output usable during triage.

Separate detection from notification
HTML generation, CLI output, and Mattermost delivery follow scoring. Keeping the analysis result distinct from its delivery channel supports investigation even when notification needs troubleshooting.

Evolve the signal without rewriting the workflow
The enhanced V5 source adds reporting-entity validation and a spike-detection path alongside ensemble voting. Both feed the same severity and reporting stages; these are source variants, not proof that every environment runs V5.

HOW IT WORKS

Load and validate the input
The Python entry point selects one or more CSV inputs. It supports summary-shaped values and a time-series preparation path, then normalizes values into an analysis table.

Derive and standardize features
The detector derives deviation, ratio, and variability features from the input and standardizes the feature matrix before fitting the models.

Evaluate multiple anomaly signals
The reviewed ensemble fits and predicts on the prepared batch. Model votes are combined; the enhanced V5 variant also evaluates a separate spike signal and identifies newly observed reporting entities.

Rank and explain candidates
Severity rules classify candidates and retain the underlying feature values. Normal observations remain distinguishable from anomalies in the reporting output.

Deliver and retain the result
The pipeline produces CLI and HTML reports, attempts configured Mattermost notification, archives the input, and applies file/log retention. The reviewed entry point is batch-oriented; a continuously running stream processor is not assumed.

ARCHITECTURE BOUNDARIES

The enhanced time-series function describes historical statistics as “30-day” values, but the reviewed code computes over the values supplied in the file rather than enforcing a 30-day cutoff. The public architecture therefore calls this the supplied historical window.

The models are fitted on the prepared batch; the code does not establish a separately validated forecasting model or a published precision/recall evaluation.

An anomaly is an investigation signal, not proof of a platform incident. Input quality, low-volume entities, and missing or zero variance affect interpretation.

The file-processing entry point is implemented. The external schedule, production host, and actual notification delivery rate are not established by the reviewed files.
