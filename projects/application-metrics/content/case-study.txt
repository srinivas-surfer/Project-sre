Peak Traffic Metrics Collector

WHY IT STARTED

A daily request total does not show the size or timing of a short traffic burst. Capacity review and peak-event preparation need evidence at different time scales, and that evidence may be spread across several environments and reporting entities.

The project addresses repetitive discovery and aggregation work: locating the relevant entity/index combination, selecting the same review window, running several interval queries, and assembling results for comparison.

I implemented a collector that performs those steps systematically and lets OpenSearch calculate peak buckets server-side. The output is a consolidated table plus CSV and JSON artifacts. It supports capacity investigation; the source does not demonstrate an automatic scaling decision or prove a particular infrastructure-cost reduction.

WHAT CHANGED

An engineer needs to repeat searches across entities, services, and intervals, then reconcile results and time zones before comparing the peaks.

One CLI-supplied review window is normalized to UTC bounds. The script discovers entities and candidate index patterns, runs the interval/service query combinations, and saves a consolidated result with peak counts and timestamps.

IMPLEMENTATION DECISIONS

Compute peaks in the search engine
The query combines date_histogram with max_bucket, so the search backend calculates the maximum bucket count. The collector does not need to download all raw request documents to count them locally.

Keep interval semantics explicit
A maximum one-second bucket, one-minute bucket, and one-hour bucket describe different windows. Keeping the interval in each result prevents a large aggregate count from being presented as a per-second rate.

Discover scope before querying
Discovery functions look for reporting entities and suitable index patterns. This reduces the need to prepare every entity/index combination manually, while still depending on query coverage.

Retain both human and machine outputs
The script prints a summary and writes CSV and JSON. This supports a review spreadsheet as well as later programmatic analysis without repeating collection.

HOW IT WORKS

Accept and normalize the review window
The command line accepts start and end times in the supported local time zone. The parser converts them to UTC epoch milliseconds and makes the selected end minute inclusive.

Discover the collection scope
For each configured environment, the collector queries available reporting entities and discovers a corresponding index pattern. A wildcard fallback is present when discovery does not find a specific pattern.

Run interval/service combinations
The collector iterates over configured time-bucket intervals and service categories for each entity, applying the same time bounds to the queries.

Calculate the peak in OpenSearch
A date histogram groups matching documents by fixed interval; a max_bucket pipeline aggregation returns the largest bucket and its key. The collector also records supporting counts and scope metadata.

Consolidate and export
Successful results are combined, summarized in the console, and written to timestamped CSV and JSON files. Failed queries are reported and do not become fabricated metric rows.

OUTCOMES

Less repetitive peak-query preparation
Discovery and nested collection loops replace repeated manual setup for each entity, service, and interval.
Implemented automation; no measured engineering-hours saving supplied.

More precise capacity-review evidence
Peak counts retain their bucket interval and timestamp rather than collapsing every observation into a daily total.
Supported by the aggregation/output structure; actual capacity gains are not measured.

Reusable analysis artifacts
CSV and JSON retain the consolidated results for review and downstream analysis.
Implemented export capability; this collector is not an autoscaler or cost-optimization engine.

ARCHITECTURE BOUNDARIES

Log-document counts represent traffic only to the extent that the source logging/filtering captures the intended requests. They are not automatically unique user sessions or completed orders.

The query reads hits.total, whose relation can indicate a lower bound unless exact total tracking is enabled. The reviewed code does not establish exact totals for every query volume.

Only non-empty buckets are requested. A one-second peak is a maximum fixed bucket count, not a rolling-window throughput measurement.

Discovery and query failures can leave incomplete coverage. Large windows with very fine buckets may also encounter aggregation limits. The output should be reviewed for completeness before capacity decisions.
